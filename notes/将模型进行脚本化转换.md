在将模型转换为 TorchScript 之前调用 `export_model.eval()` 是**至关重要**的一步，主要原因如下：

### 1. 固化推理行为（核心原因）
PyTorch 中的某些层在训练和推理时的行为完全不同。`eval()` 会将这些层永久切换到推理模式：

| 层类型 | 训练模式 (`train()`) | 评估模式 (`eval()`) | 不切换的后果 |
| :--- | :--- | :--- | :--- |
| **BatchNorm** | 使用当前 batch 的均值/方差，并更新 running stats | 使用训练期间累积的固定 running stats | TorchScript 会捕获错误的 BN 逻辑，导致部署后输出完全错误 |
| **Dropout** | 随机丢弃神经元 | 完全关闭，所有神经元参与计算 | 部署后每次推理结果都不一致，且精度下降 |

> ⚠️ **关键点**：`torch.jit.script` 会**静态分析并编译模型的代码逻辑**。如果在 `train()` 模式下进行脚本化，TorchScript 会把 Dropout 的随机掩码逻辑和 BatchNorm 的动态统计逻辑"烧录"进模型中。即使你之后在 scripted 模型上调用 `.eval()`，也**无法改变**已经编译好的图结构。

### 2. 启用 TorchScript 的推理优化
TorchScript 编译器在检测到模型处于 `eval()` 模式时，会自动应用一系列针对推理的图优化：

-   **算子融合**：将 Conv + BatchNorm + ReLU 融合为单个高效算子
-   **常量折叠**：将推理时不变的计算提前求值
-   **死代码消除**：移除仅在训练中使用的分支（如梯度相关逻辑）

这些优化只有在 `eval()` 状态下才会被触发，能显著提升部署后的推理速度并减小模型体积。

### 3. 确保与训练代码解耦
`torch.jit.script` 要求模型的前向传播代码必须是自包含的、不依赖外部状态的。`eval()` 确保了模型的所有内部状态（如 BN 的 buffer）都被设置为推理所需的确定性值，使得编译出的 TorchScript 模型成为一个**完全独立、可移植**的推理单元，不再需要原始的 Python 类定义或训练配置。

### 💡 最佳实践提醒
```python
# ✅ 正确顺序
export_model.eval()                    # 1. 先切到评估模式
scripted = torch.jit.script(export_model)  # 2. 再编译

# ❌ 错误顺序
scripted = torch.jit.script(export_model)  # 编译了训练模式的逻辑
scripted.eval()                            # 太晚了！已编译的图不会改变
```

简而言之：**`eval()` 必须在 `torch.jit.script` 之前调用**，因为它决定了被编译进 TorchScript 的究竟是"训练逻辑"还是"推理逻辑"。这一步做错了，部署的模型将无法正常工作。
